# Автоматическая установка HA и AliceTG_Bot на `ha-vps`

Этот каталог содержит исполняемый Linux-адаптер для координатора автоматических
обновлений. Он не создаёт HTTP-сервер и не открывает административный порт. Вход —
фиксированная цель и полный Git SHA; все пути, Compose services и credentials
задаются один раз в защищённой конфигурации сервера.

## Что установлено по исходникам 27.11.2026

| Цель | Источник | Установка и проверка |
| --- | --- | --- |
| Samsung | `decorum-guy/artem-control-center` | Штатный Windows updater; описан в документации координатора. Этот Linux-адаптер Samsung не обслуживает. |
| Telegram-бот | `decorum-guy/AliceTG_Bot` | У бота свой репозиторий. Его [`deploy-telegram-bot.sh`](https://github.com/decorum-guy/AliceTG_Bot/blob/85ba53eb7e5f30f875cf96fb305600a0e1527e45/scripts/deploy-telegram-bot.sh) собирает только `telegram-bot` с loopback overlay родительского HA Compose. |
| HA: управляемые файлы | `artem-control-center/integration-patches/home-assistant/config/` | Явно выбранные package YAML и четыре файла `custom_components/artem_panel`; остальная конфигурация HA сохраняется. |
| HA Core: версия контейнера | Не определяется коммитом бота | Необязательный файл желаемого образа в `artem-control-center`, только точный OCI digest. При отсутствии файла текущий образ сохраняется. |

В доступных GitHub-репозиториях не найден отдельный репозиторий конфигурации HA.
Документы указывают на внешний каталог `Homeassistant` на Mac и родительский
Compose на VPS. Это результат чтения репозиториев, не SSH-инвентаризация сервера.
Связь бота с HA не делает его репозиторий владельцем всех настроек HA.

В существующем бот CI не было запуска по `push: main`. Исправление подготовлено
в [AliceTG_Bot PR #45](https://github.com/decorum-guy/AliceTG_Bot/pull/45).
До его merge и первого успешного **main-push** запуска координатор не должен
устанавливать бот. Зелёный PR run не заменяет этот gate.

## Контракт адаптера

```text
python3 /opt/artem-auto-deploy/deploy_home_server.py \
  --config /etc/artem-auto-deploy/home-server-deploy.json \
  --target telegram-bot \
  --sha <полный SHA из проверенного координатором main>
```

Вторая допустимая цель — `home-assistant`. Shell-команды, URL, пути и имена
контейнеров из webhook не принимаются. Координатор проверяет CI до вызова;
адаптер независимо сверяет exact origin, чистое дерево и текущий `origin/main`.
Локальный файл конфигурации не заменяет GitHub CI-проверку.

Результат — одна JSON-запись с `target`, `status`, `revision` и
`attemptedRevision`. Exit `0` означает только `deployed` или `up_to_date` после
проверки. У `rolled_back` `revision` указывает **проверенную прежнюю ревизию**, а
код выхода равен `1`. При неизвестной прежней ревизии, незавершённом запросе или
неподтверждённом откате результат остаётся `failed`; координатор блокирует
следующие установки до сверки оператором.

До изменения runtime и до появления незавершённого journal ошибка возвращает
`deferred`: например, `main` изменился между проверкой координатора и `git fetch`,
либо maintenance lock занят. Следующий проход может заново проверить состояние;
обычный новый push не блокирует сервер как неизвестная production-операция.

Рабочий SHA сам по себе не доказывает версию старого бота. Для первоначального
образа без revision label адаптер сравнивает Git blob hashes всех `app/*` и
`requirements.txt` с файлами внутри контейнера. Изменяемый bind mount исходников
или несовпадение останавливают установку. Новые образы и контейнеры получают
revision labels; после установки сверяются label, image ID и readiness.

## Telegram-бот

Последовательность:

1. Проверить прежний runtime, текущий main и отсутствие локальных изменений.
2. Отклонить автоматический переход при изменениях `app/planning/sql/`,
   `migrations.py` или `db.py`: без отдельной проверки совместимости нельзя
   обещать безопасный возврат старого кода к новой SQLite-схеме.
3. Создать **и проверить** штатную зашифрованную A8 Planning backup внутри
   текущего контейнера. Для этого используется существующий
   [`app.planning.backup`](https://github.com/decorum-guy/AliceTG_Bot/blob/85ba53eb7e5f30f875cf96fb305600a0e1527e45/docs/PLANNING_BACKUP_RESTORE.md),
   а не копирование работающей SQLite базы.
4. Переключить чистый checkout на точный SHA, собрать отдельный образ
   `artem-auto/telegram-bot:<SHA>` и закрепить его в приватном Compose overlay.
5. Пересоздать только бот с `--no-deps --no-build --pull never`, выполнить
   существующий loopback verifier и `/health/ready`.
6. При известном отказе вернуть прежние commit и image ID, перечитать readiness.
   Данные Planning, расписания и секреты автоматически не откатываются.

Адаптер использует ту же Compose-топологию, что штатный helper, и обязательно
подключает `compose.control-center-loopback.yml`. Он сам выполняет отдельные
build/recreate шаги, потому что исторический helper не принимает дополнительный
overlay с закреплённым образом и revision labels. Ни Caddy, ни HA, ни прокси при
обновлении бота не перезапускаются.

Readiness бота требует Telegram, HA и timing helpers. Если, например, недоступен
`kz-bot`, проверка не подменяется одной работающей HTTP-страницей. Это может
остановить обновление, но не перенастраивает proxy и не создаёт уведомления.

## Home Assistant: файлы и образ

`managedFiles` — список **точных** пар source/destination. Разрешены:

- package YAML под `integration-patches/home-assistant/config/packages/` →
  `packages/`;
- только `__init__.py`, `request_gateway.py`, `manifest.json`, `services.yaml`
  интеграции `custom_components/artem_panel`, обязательно вместе и без смены
  относительных имён.

Нельзя управлять `configuration.yaml`, `secrets.yaml`, `.storage`, произвольным
custom component или произвольным файлом через этот список. Включение packages
и публикация сущности «Панель» в Яндексе остаются первоначальной настройкой.

Все файлы читаются из одного проверенного SHA. Адаптер делает приватную копию
действующей конфигурации, кладёт туда кандидат и запускает `check_config` в
одноразовом контейнере с `--network none`. HA-сервер в этом контейнере не
запускается. Копия для проверки удаляется и при ошибке. Перед применением
сохраняются прежние версии всех затронутых файлов. Замены выполняются атомарно
для каждого файла в одной операции обслуживания; HA пересоздаётся только после
завершения всей группы. Затем проверяются API, наличие ожидаемых entity IDs и
точные хеши установленных файлов. Ошибка возвращает прежние файлы и образ.

`expectedEntities` проверяет, что конфигурация загрузила нужные сущности.
Состояние `unavailable`/`unknown` не считается отказом HA: Samsung может быть
выключен, пока сервер работает нормально. Физическое подтверждение яркости —
отдельная проверка.

Если файлы и выбранный образ не изменились, target возвращает `up_to_date` без
перезапуска HA. Поэтому изменение оформления панели не перезапускает дом.

### Необязательное изменение HA Core

`imageManifest: null` сохраняет действующий image ID. Для управляемого обновления
Core локальный агент сначала устанавливает фактическую версию, recorder storage
и восстановление, затем добавляет в репозиторий небольшой файл:

```json
{
  "schemaVersion": 1,
  "image": "ghcr.io/home-assistant/home-assistant@sha256:<64 hex>"
}
```

Placeholder выше намеренно не является допустимым образом. В Git должен попасть
проверенный реальный digest; адаптер отвергает `stable`, `latest`, обычные теги и
другие registries. Изменение этого файла проходит review/CI как любой релиз.
Путь указывается в `imageManifest`, а `allowImageChange` и
`sqliteRecorderConfirmed` включаются только после проверки VPS.

При смене image ID адаптер останавливает **только HA**, подтверждает остановку,
делает полную согласованную приватную копию `/config` с SQLite и `.storage`, и
лишь затем запускает новый образ. Старые каталоги backups и `.git` не копируются
и не уничтожаются. При отказе HA снова останавливается; кандидатный `/config`
сохраняется для разбора, затем восстанавливается полная копия и прежний образ.
Неполная копия никогда не применяется. Каталоги с symlink/special files
отклоняются; проверяется свободное место. Внешний recorder требует отдельного
адаптера согласованного backup/restore — данный код его не изображает.

Это существенно для HA: официальный runbook предупреждает, что после возврата
старого контейнера данные могут оставаться в новом формате до восстановления
[backup](https://www.home-assistant.io/common-tasks/container/). Один `docker pull`
не является процедурой безопасного обновления и отката.

## Первоначальная установка локальным агентом

1. На Mac использовать `ssh ha-vps`, сверить фактические host, Compose project,
   services, bind mount `/config`, работающие image IDs, checkout origin/SHA и
   права. `home-server-deploy.example.json` содержит placeholders, не текущие
   пути сервера. Не печатать `.env`, `runtime.env`, Compose с раскрытыми secrets
   или токены.
2. Сделать исходные backups по действующим runbooks. Проверить A8 backup/verify
   бота и восстановимость HA. Установить HA packages include, файлы яркости и
   Yandex exposure согласно документации функции. Обновление файлов не может
   само опубликовать новое устройство в аккаунте Яндекса.
3. Установить **отдельную копию** `deploy_home_server.py` под
   `/opt/artem-auto-deploy/`, root-owned и без записи для группы/прочих.
   Не запускать адаптер из checkout, который он будет переключать. Обновление
   самого привилегированного адаптера — отдельная контролируемая установка.
4. Скопировать пример конфигурации в `/etc/artem-auto-deploy/` с правами
   `0600`, заменить пути после сверки, создать state directory `0700`. HA token
   оставить в отдельном `0600` файле; HTTP-клиент читает его без передачи в argv.
   Требуются Linux, Python 3.11+, Git, Docker Compose и Bash. Этот процесс имеет
   Docker-права: запускать его может только доверенный установленный координатор.
5. В конфигурации координатора указать установленный адаптер и его отдельный
   защищённый конфигурационный файл. Пути выбираются при установке и не меняются
   webhook-запросом. Адаптер дополнительно берёт существующий lock
   `/run/lock/artem-control-center-home-maintenance.lock`, поэтому не работает
   одновременно с ручной командой обслуживания из панели.
6. Сверить current image/runtime baseline и readonly конфигурацию. Включить
   нужные targets; сначала один выпуск с наблюдением, затем unattended worker.
   Для бота сначала merge [PR #45](https://github.com/decorum-guy/AliceTG_Bot/pull/45)
   и зелёный CI на main SHA. Не отключать gate для первого запуска.
7. В действующие ручные maintenance процедуры включить приватный
   `<stateDir>/<target>/active-image.json` после loopback overlay, иначе
   последующий ручной Compose rebuild может отменить закрепление образа.
   Не публиковать Panel Agent или Docker API наружу. Существующие Caddy, SSH и
   `kz-bot` не перестраивать для этой функции.

Текущий root-owned `home-maintenance` принимает один `COMPOSE_OVERLAY`. Пока
оператор не объединит его loopback/image pins в согласованную установку, ручное
`update-ha` из панели может сменить образ независимо от manifest. Проверить этот
конфликт при первоначальной настройке: обновления версии HA должны иметь одного
владельца. Обычный restart существующего контейнера pin не меняет.

## Тайм-аут, восстановление и отключение

Docker CLI timeout не доказывает, что Docker daemon отменил действие. В таком
случае адаптер сохраняет `pending.json` со статусом `outcome_unknown`, не
перезапускает повторно контейнер и не гоняет откат параллельно возможной операции.
Следующие попытки заблокированы. Незавершённый journal после падения процесса
также блокирует автоматическое продолжение.

Оператор останавливает координатор, сверяет фактические container image ID,
revision label, managed-file hashes и readiness с приватным журналом, затем
заканчивает/откатывает адресную операцию. Только после доказанной целостности
архивируются pending и coordinator attempt и задаётся проверенная база новой
попытки. Удалять journal ради снятия ошибки без проверки нельзя.

Для отключения остановить worker и выставить target `enabled: false`. Работающие
контейнеры, данные и подтверждённые backups остаются на месте. Транзакции и
резервные копии сохраняются локально; их retention устанавливает оператор после
проверки восстановления. Скрипт не удаляет единственную подтверждённую копию и
ничего не загружает в GitHub.

## Проверки этого изменения

```bash
python -m unittest discover -s integration-patches/auto-deploy/tests -p 'test_*.py' -v
```

Тесты Linux-адаптера с POSIX permissions выполняются на Linux и явно пропускаются
на Windows. Чистая URL-проверка остаётся кроссплатформенной. Проверки координатора
и Windows updater имеют собственные наборы; Linux Docker-тесты не объявляются
проверкой Windows.

Тесты используют управляемые ответы Git/Docker/HTTP, временные файлы и отдельную
проверку реального subprocess redaction. Проверены exact main/origin, dirty
checkout, source hashes первоначального бота, migration gate, backup verification,
изолированная проверка HA, все управляемые файлы, rollback, неполный backup,
неизвестный результат команды и отсутствие повторного dispatch. Это не результаты
живого Docker/VPS: SSH, перезапуски HA/бота и production mutations в облачном
раунде не выполнялись.
