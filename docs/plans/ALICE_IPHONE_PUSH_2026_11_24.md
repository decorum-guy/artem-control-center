# Нативный push Алисы на iPhone — история проверки

## Актуальный статус, 25.11.2026

Владелец подтвердил push «Б, кедр» от напоминания, созданного и перенесённого обычной формой Samsung на базе `b1ee01cf`. Пустой `origin_device_id` совместим с доставкой в этом случае. Причина прежних недоставок и точное время доставки неизвестны; изменение #377 не является доказанной причиной успеха.

**Дополнительные живые прогоны остановлены владельцем.** Второе phone-only и режим «На оба» не проверены. Ниже сохранён исторический протокол 24.11.2026; он не является поручением возобновлять A/B, создавать напоминания или снова запрашивать действия iPhone. [Результат, аудит #376/#377 и следующий выпуск](ALICE_PUSH_REVIEW_AND_RELEASE_2026_11_25.md) имеют приоритет над прежними заданиями ниже.

## Историческая цель и состояние на 24.11.2026

24.11.2026 владелец прямо поставил проверку push на iPhone первым текущим заданием. Он повторно подтвердил важный контроль: напоминание, созданное в официальном «Доме с Алисой», прислало push. Следует исследовать различие нашего пути создания.

Проверен код кандидата #376 `b1ee01cf55dc4751771d6afc1dd9082f8a4f9039`, основанного на принятом #375 `ae376d22`. Файл `station_reminders.py` в diff между этими ревизиями не менялся. Main по GitHub остаётся `2b361918f11ba2ae40805fa65bcdbe1b3f6f99d8`. Работа штатного 8787 и preview 8797/8798 — сведения отчёта исполнителя, без нового SSH-чтения автора этого документа.

**На начало расследования root cause недоставки не был доказан.** Различие `origin_device_id` рассматривалось как гипотеза; позднейший успешный Б опроверг обязательность непустого поля для проверенного пути. Это не готовый параметр исправления. HTTP 200, сохранённый `send_push=Enabled`, наступление срока и озвучка на Станции не доказывают появление push на iPhone.

В этом раунде оркестратор и агенты читали код/отчёты/первичные материалы. Исполнен фактический backend с управляемым HTTP и тестовыми реквизитами; оркестратор повторил прогон, exit 0. Новых живых напоминаний, push, SSH или действий на iPhone этим аудитом не выполнялось.

## Уже известное наблюдение

[Прежний отчёт Samsung](https://github.com/decorum-guy/artem-control-center/blob/b1ee01cf55dc4751771d6afc1dd9082f8a4f9039/docs/plans/SAMSUNG_AUTONOMOUS_RESULTS_2026_11_24.md), раздел «Повторная приёмка озвучки и устойчивость списка»:

- Три записи из обычной формы были явно `phone-only`, на 06:03, 06:07 и 06:11 МСК.
- Яндекс вернул личную запись и включённый push; владелец не увидел уведомления. Последняя проба была без VPN телефона.
- Затем владелец создал контроль в официальном iPhone-приложении и подтвердил push.
- У контрольного payload был `origin_device_id`; у записи панели — нет.
- Влияние поля на маршрут тогда не исследовали до результата.

Отчёт не уточняет, было поле в исходном create-запросе приложения или только в ответе/сохранённой записи. Не объявлять его идентификатором физического iPhone или обязательным входным полем без проверки. Не генерировать значение и не переносить случайный ID.

Начальный выбор формы `station` не объясняет описанные три отказа: в отчёте явно проверялся `phone`. Новый прогон всё равно должен фиксировать фактический отправленный режим.

## Что делает наш путь

[Backend](https://github.com/decorum-guy/artem-control-center/blob/b1ee01cf55dc4751771d6afc1dd9082f8a4f9039/apps/panel-agent/src/panel_agent/station_reminders.py):
`POST /api/v1/station/reminders` вызывает фиксированный `rpc.alice.yandex.ru/gproxy/create_note`. Это прямое создание Calendar Notes из Samsung, не HA-команда колонке.

Клиент использует отдельные защищённые reminder credentials с `client_uuid` и cookies. В заголовках стоит `X-Ya-App-Id=ru.yandex.webstandalone.desktop`, `X-Ya-App-Type=other` и настроенный client UUID. Причинная связь desktop-контекста с push пока не установлена.

| Режим формы | push | Область записи | Озвучка |
| --- | --- | --- | --- |
| На Станцию | Disabled | Не личная, подтверждённый дом | Подтверждённая Mini 2 |
| На телефон | Enabled | Личная, без списка домов | Колонка не задана |
| На оба | Enabled | Не личная, подтверждённый дом | Подтверждённая Mini 2 |

В create `origin_device_id` не отправляется. Тестовая схема чтения допускает его на уровне `reminders[0]`. После создания код проверяет время, play_location, send_push, personal и home IDs. Origin/получатель/регистрация push не проверяются. Нормализованный API оставляет только id/title/dueAt/timezone/repeats/version.

Адресный прогон показал:

- Все три режима формируют ожидаемые push/personal/home/Station параметры.
- Ответ с отсутствующим origin и ответ с произвольным синтетическим origin принимаются одинаково; в проекцию поле не попадает.
- Если тестовый сервер меняет Enabled на Disabled, возвращается `502 unconfirmed`. Проверка не ограничена HTTP 200.
- Это ограничение диагностики маршрута, не доказательство причины недоставки.

[UI](https://github.com/decorum-guy/artem-control-center/blob/b1ee01cf55dc4751771d6afc1dd9082f8a4f9039/apps/dashboard/src/AliceRemindersSection.tsx) при создании отправляет delivery, при переносе — только новое время/версию. Backend update передаёт note_id/status/schedule и сверяет сохранение play_settings; отдельной сверки origin нет.

Старые [настройки доставки](https://github.com/decorum-guy/artem-control-center/blob/b1ee01cf55dc4751771d6afc1dd9082f8a4f9039/apps/dashboard/src/features/settings/ReminderDeliverySettings.tsx) с Telegram/Home Assistant обслуживают другой механизм. Нативная форма их не использует. Переключение этих каналов, исправление Telegram или восстановление kz-bot не являются подтверждённым решением нативного push Яндекса.

## Официальные материалы

В [справке Яндекса](https://alice.yandex.ru/support/ru/station/settings/reminder) озвучка на Станции и push описаны отдельно. Для напоминаний приглашённого участника указан получатель — владелец дома; общая видимость записи не доказывает тождество получателя.

[Инструкция Яндекса для iOS](https://inclusion.yandex.ru/tutorials/smart-home-with-alice-ios-part2) различает настройки напоминаний, созданных через колонку, и выбор «Телефон» у конкретной записи в форме. При сравнении фиксировать именно назначение контрольной записи, не предполагать его по глобальному тумблеру.

Это описание пользовательского интерфейса, не опубликованная спецификация Calendar Notes payload. В ограниченном поиске первичный публичный контракт create/origin/push не найден. Семантику поля нужно установить наблюдением доступного официального клиента и ограниченным экспериментом.

## Исторический протокол живого сравнения — сейчас остановлен

1. Сверить фактический preview/SHA и endpoint. Основной 8787 ещё старый; не перепутать форму Planning с нативной `/api/v1/station/reminders`. Подготовить один диагностируемый экземпляр, без дополнительных получателей голосовых событий/BLE.
2. До действий владельца подготовить тихое чтение и локальную обезличенную диагностику. Сырые cookies, account/device IDs и чужие напоминания не публиковать. Сохранять наличие полей, типы и согласованные метки равенства объектов.
3. Получить запись A из официального приложения с явно выбранным телефоном. Если доступного управления iPhone нет, попросить владельца одно конкретное действие: создать названный контроль на близкое будущее с запасом для чтения.
4. Создать запись B через обычную форму Samsung с режимом phone и отличимым названием/сроком. Зафиксировать фактический POST, create response и server readback до наступления срока. У A сначала не менять время и доставку: контроль должен оставаться независимым.
5. Использовать тот же iPhone, сопоставимое состояние приложения/экрана и сети; во время пары не менять разрешения, VPN и Focus. Наблюдение владельца или доступный реальный экран подтверждают наличие push. Отдельно записать ожидаемое/фактическое время, дубли и озвучку.
6. Если A приходит, B нет — приоритетно исследовать create/client/recipient. Если перестал приходить и A, зафиксировать смену условий и только тогда диагностировать общие условия уведомлений. Не выдавать старый успех A за новый замер.

Сравнивать раздельно исходный запрос (если реально доступен), ответ создания и сохранённую запись. Значимые группы:

- аккаунт авторизованного создателя и владелец дома/получатель;
- personal/home и выбранные устройства;
- send_push/play_settings и прочие реально присутствующие поля доставки;
- origin_device_id: уровень, наличие, происхождение и сохранение;
- client UUID/app identity и их связь с авторизованной установкой приложения;
- schedule/timezone/offset и время принятия сервером.

## Локализация после A/B

Не менять одновременно заголовки, область записи и origin. Выбрать следующий эксперимент по конкретному отличию.

Полезны отдельные тестовые записи:

- Созданная официальным приложением запись, которую переносит панель: сохранятся ли origin/доставка и придёт ли push? Это отделяет create от update.
- Созданная панелью запись, у которой официальный клиент заново сохраняет выбор телефона: какие поля изменятся и появится ли push? Нужен подтверждённый update клиента; простое открытие формы не считается изменением.

Не выполнять оба теста автоматически, если первый уже локализует проблему. Сначала установить, задаёт ли официальный клиент origin или сервер выводит его из сессии/регистрации. Изучать доступный официальный клиент адресно. Любые допустимые эксперименты с реквизитами — только с подтверждённой собственной записью/устройством; не подменять произвольные app IDs и не перебирать значения.

Исправление реализовать в отдельной ветке от актуального кандидата, с явной базой. При изменении времени сохранить весь подтверждённый маршрут доставки. Нормализованная диагностика может показывать назначение и наличие origin; полный upstream payload и credentials браузеру не передавать. Не заявлять receipt, которого API не предоставил.

## Прежние критерии полной приёмки — выполнены частично

- Два последовательных напоминания из обычной формы Samsung в режиме phone дают реальный push на iPhone.
- Один тест both отдельно подтверждает push и голос Mini 2.
- Перенос ещё не наступившей тестовой записи сохраняет доставку и приводит к уведомлению в новое время; результат не подменяется серверным EXPIRED.
- Сохраняются тихое чтение, пресеты времени, синхронизация с приложением и ограничения доступа.
- Контрольные записи удаляются адресно после наблюдения; чужие записи не меняются. Нет бессрочных тестовых расписаний и новых каналов уведомлений.
- Если причина остаётся неизвестной, отчёт содержит точные пары запрос/ответ/наблюдение, опровергнутые гипотезы и конкретную границу доступа. Успех не объявляется по одному Enabled.

Разрешение на живые прогоны относилось к исходному заданию 24.11.2026. Последующее сообщение владельца остановило дополнительные тесты. Не продолжать их на основании этого исторического раздела.

Следующий рекомендуемый этап после частичного положительного результата — общий кандидат #375–#377 с актуальным манифестом. Merge/штатная установка остаются отдельным поручением. Не приписывать неизвестной причине доказанное исправление; хранить отдельно фактическую доставку, программные проверки и оставшиеся ограничения. Артефакты и секретные дампы в GitHub не загружать.
