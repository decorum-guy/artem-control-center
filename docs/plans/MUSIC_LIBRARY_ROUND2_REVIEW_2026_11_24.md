## 3. Открытая приёмка: короткий ответ Мини 2

### Подтверждено отчётом и кодом

Владелец услышал выбранный трек и подтвердил продолжение музыки. Голосовая команда сохранения зарегистрирована, HA принял запрос ответа, но владелец ответа не услышал. Озвучка остаётся непринятой. Увеличение громкости в том прогоне не решило проблему; исполнитель вернул исходные 50%.

Panel Agent вызывает `media_player.play_media` с `media_content_type=text` и фиксированной фразой. HTTP success проверяется, но звукового подтверждения нет. `AliceVoiceFeedback` отмечает принятие и не повторяет исходную музыкальную операцию при ошибке ответа. Источники: [sender](https://github.com/decorum-guy/artem-control-center/blob/571bf39f445fa27cc898b950bcc9dfd3e0769bb7/apps/panel-agent/src/panel_agent/home_assistant.py#L134-L152), [feedback](https://github.com/decorum-guy/artem-control-center/blob/571bf39f445fa27cc898b950bcc9dfd3e0769bb7/apps/panel-agent/src/panel_agent/alice_voice_feedback.py).

### Что показывает AlexxIT v3.22.3

У `text` есть два пути. При local_state интеграция отправляет по Glagol `serverAction` / update_form `personal_assistant.scenarios.quasar.iot.repeat_phrase` с `phrase_to_repeat`. В облачном режиме она строит TTS-сценарий, обновляет его и запускает через Quasar.

Облачный `send()` использует один `device.scenario_id`: PUT нового содержимого, затем POST запуска. Этим же методом идут разные команды, включая облачные громкость и продолжение музыки. Поэтому отсутствие ожидаемой фразы в более позднем снимке служебного сценария **не доказывает**, что она никогда не записывалась. Конкурирующая запись или осмотр после другой команды — гипотезы, а не установленная причина конкретного сбоя.

Источники: [YandexStation text/local/cloud](https://github.com/AlexxIT/YandexStation/blob/v3.22.3/custom_components/yandex_station/core/yandex_station.py#L955-L1026), [Quasar send](https://github.com/AlexxIT/YandexStation/blob/v3.22.3/custom_components/yandex_station/core/yandex_quasar.py#L314-L342), [TTS payload](https://github.com/AlexxIT/YandexStation/blob/v3.22.3/custom_components/yandex_station/core/yandex_quasar.py#L103-L138), [update_form](https://github.com/AlexxIT/YandexStation/blob/v3.22.3/custom_components/yandex_station/core/utils.py#L97-L114).

### Следующий эксперимент и реализация

1. На актуальном Samsung проверить целевую entity/устройство, активный транспорт HA и единственного получателя голосовых событий. Собрать обезличенную цепочку одной операции: событие → результат сохранения → выбранная фраза → отправка → ответ транспорта. Не объявлять HTTP 200 или WebSocket ack доказательством звука.
2. Для облачного пути прочитать служебный сценарий и историю конкретного запуска с правильными ID и временем. Сопоставить с соседними командами, включая громкость. Не удалять и не пересоздавать сценарии вслепую; внешнюю интеграцию использовать для чтения.
3. Провести ограниченную пробу одной фиксированной фразы через существующее локальное соединение Samsung → Mini 2, используя форму из AlexxIT. Для доставки этой команды не нужен HA на Samsung. Это локальная доставка команды; автономный офлайн-синтез речи этим не обещается. Сначала подтвердить применимость на данной Mini 2.
4. Если локальная проба работает, реализовать узкий sender коротких ответов в Panel Agent на существующей сессии. Не создавать отдельное соединение на каждую вкладку, универсальный JSON/URL/текстовый proxy или новый путь исполнения музыкальных команд. Разрешённые cue/text выбирает backend. Проверять права перед отправкой, ограничить ожидание, отбрасывать устаревший ответ и не повторять неясную отправку автоматически.
5. Если исправляется существующий путь через HA, обосновать доказанной причиной, почему его достаточно. Не выбирать новый транспорт только на основании отсутствия фразы в позднем снимке.
6. Проверить произнесение в idle и во время музыки, один реальный итог голосового сохранения, отсутствие двойного ответа, сохранение трека и исходной громкости. Нужное слуховое наблюдение получить у владельца. Самостоятельно выполнить диагностику и подготовку, не просить повторные общие разрешения.

## 4. Кондиционер: отдельный диагностический хвост

По отчёту HA подтвердил изменение цели 32 → 31 °C при off, затем через 1,5 секунды fan изменился five → one. Это успешная проверка изменения заданной температуры на уровне HA, не измерение температуры воздуха. Неизвестное изменение fan не возвращает R4 в открытое состояние.

Код `set_temperature` передаёт только `entity_id` и `temperature`; отдельный путь `set_fan_mode` существует отдельно. Этим не доказана причина изменения вентилятора. [Климатический executor](https://github.com/decorum-guy/artem-control-center/blob/571bf39f445fa27cc898b950bcc9dfd3e0769bb7/apps/panel-agent/src/panel_agent/home_assistant_actions.py#L564-L574).

Сначала без новых физических команд сопоставить аудит обоих процессов панели, доступные context/history/logbook/trace HA и фактическую реализацию интеграции кондиционера. Проверить, не отправляет ли она полное состояние или default fan при изменении температуры. Если данных нет — сохранить «причина не установлена». Не приписывать изменение владельцу или устройству без свидетельства.

Остановка автоматического восстановления была обоснованной: появилась отдельная неизвестная запись состояния. Не возвращать 32 °C автоматически после этого аудита. Последнее сообщённое состояние — цель 31 °C, питание off; перед дальнейшей работой перечитать фактическое состояние.

## 5. Предлагаемое продуктовое расширение: плейлисты Яндекса

R1–R5 закрыты; следующий самостоятельный объём развития — такой же выбор плейлистов в блоке Яндекса. Это расширение исходного «Мне нравится», а не оставшийся дефект предыдущего раунда.

В текущем [yandex_library.py](https://github.com/decorum-guy/artem-control-center/blob/571bf39f445fa27cc898b950bcc9dfd3e0769bb7/apps/panel-agent/src/panel_agent/yandex_library.py) catalog возвращает только `likes`, а tracks принимает только его. UI и общий библиотечный backend уже умеют каталоги, выбор и сохранение просмотра.

В проверенном upstream `MarshalX/yandex-music-api` на `9ca132e5c18a72aab779c1fc68c169380a9357d0` есть:

- `users_playlists_list` для собственных плейлистов;
- `users_likes_playlists` для понравившихся плейлистов;
- `users_playlists(kind, user_id=owner_uid)` для выбранного списка;
- поля cover, og_image, track_count и revision в Playlist.

Источники: [playlists](https://github.com/MarshalX/yandex-music-api/blob/9ca132e5c18a72aab779c1fc68c169380a9357d0/yandex_music/_client/playlists.py), [likes](https://github.com/MarshalX/yandex-music-api/blob/9ca132e5c18a72aab779c1fc68c169380a9357d0/yandex_music/_client/likes.py), [Playlist](https://github.com/MarshalX/yandex-music-api/blob/9ca132e5c18a72aab779c1fc68c169380a9357d0/yandex_music/playlist/playlist.py). Это сведения из кода неофициального клиента; доступность всех этих чтений для аккаунта владельца нужно подтвердить на Samsung.

План реализации после читающего эксперимента:

1. Сохранить «Мне нравится» отдельным первым источником. Добавить собственные и понравившиеся плейлисты с настоящими обложками и понятным резервным видом при их отсутствии.
2. Идентифицировать обычный плейлист парой owner UID + kind; название не идентификатор. Дедуплицировать совпадение между own/liked по этой паре. Не выдавать все понравившиеся плейлисты за собственные.
3. Индекс треков хранить отдельно для аккаунта/плейлиста/ревизии. Текущий единственный `self.index` для likes нельзя переиспользовать между разными списками. Сохранять порядок, пару track/album, повторы и недоступные позиции.
4. Метаданные читать ограниченными порциями; не подгружать полные треки всех плейлистов при открытии страницы. Методы upstream не доказывают настоящую серверную пагинацию — отделять полученный индекс от UI-порций и честно описывать лимиты.
5. Переиспользовать исправленные refresh, подписи строк, восстановление просмотра, подсветку и текущий запуск по точному Яндекс-ID. Не дублировать музыкальный store и не возвращать отдельные запросы Станции на вкладку.
6. В этом объёме читать списки и запускать выбранный трек. Редактирование состава, массовый перенос лайков, перемешивание/очередь всего плейлиста не добавлять без отдельной продуктовой задачи.

При отсутствии доступного auth или ответа одного API продолжить независимую работу со звуком; не записывать неподтверждённую интеграцию как готовую.
