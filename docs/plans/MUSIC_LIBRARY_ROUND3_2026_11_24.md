# Третий раунд PR #374

## Яндекс Музыка

На Samsung существующая авторизация прочитала «Мне нравится», четыре собственных плейлиста и один понравившийся плейлист другого владельца. Каждый обычный список определяется парой `ownerUid/kind`. При открытии экрана загружается каталог и выбранный список. В каталог не загружаются треки остальных списков.

У двух проверенных списков Яндекс вернул полный компактный индекс за 0,33–0,48 с. Метаданные подгружаются по 40 позиций. У внешнего плейлиста Edge загрузил 40 и ещё 20 позиций. Два выбранных плейлиста показали разные настоящие обложки. Проверено на Samsung при 1280×720 и 720×1280. Порядок, повторяющиеся позиции, известная пара трек/альбом и недоступные записи сохраняются. У проверенных обычных плейлистов компактный индекс вернул только ID треков. Запуск из собственного плейлиста подтвердился свежим `playing` с точным ID за 2,1 с. Тестовый трек поставлен на паузу через панель. [Клиент Яндекс Музыки](https://github.com/MarshalX/yandex-music-api/blob/main/yandex_music/_client/playlists.py).

Смена аккаунта очищает индексы. Истёкшее продолжение одного плейлиста не применяется к другому. При ошибке обновления каталога прежний каталог остаётся доступен. Добавлены тесты разных владельцев, совпадающих названий, смены аккаунта, повторов, обновления и точного запуска в обеих ориентациях.

## Скорость вентилятора

Recorder HA связал `set_temperature` (08:55:43.974 МСК), запись 31 °C при скорости `five` (08:55:44.561) и `one` (08:55:46.063) одним контекстом. В аудите preview есть принятие и подтверждение изменения температуры. В проверенном интервале Recorder не увидел отдельный `set_fan_mode`, аудит основного процесса пуст, Logbook вернул пустой ответ, сохранённых traces кондиционера нет.

Установленный YandexStation 3.22.3 отправляет один capability `temperature`, затем перечитывает устройство. `fan_speed` соответствует отдельному setter. Источник смены скорости в облаке или на устройстве не установлен. Прочитанное в 10:35 МСК состояние было `off`, 31 °C, `one`. В этом раунде кондиционеру не отправлялись команды. [Исходник device_action](https://github.com/AlexxIT/YandexStation/blob/v3.22.3/custom_components/yandex_station/core/yandex_quasar.py#L386-L405).

## Озвучка

HA видит настроенную Мини 2 в облачном режиме. Служебный сценарий сопоставлен с той же физической Станцией. В предыдущем прогоне Recorder видит `volume_set` в 08:59:39.372 МСК, `play_media(text)` с фиксированным музыкальным ответом в 09:00:59.443 и восстановление громкости в 09:01:07.048, всё на той же entity. План изменения и запуска служебного сценария известен из кода YandexStation, но ID и времена каждого запроса в Quasar для того прогона не записаны. Причина тишины не установлена. Музыкальные фразы переведены на локальную доставку по общему Glagol. Отправка ограничена одной репликой, проверяет права и прекращается по тайм-ауту. TV feedback по-прежнему использует HA. [Локальный формат YandexStation](https://github.com/AlexxIT/YandexStation/blob/v3.22.3/custom_components/yandex_station/core/utils.py#L88-L105).

Владелец услышал диагностические фразы. Glagol подтвердил приём за 375 мс на паузе и 328 мс на фоне музыки. Через пять секунд после второй отправки Станция продолжала отдавать свежий `playing` с тем же ID. Эти задержки относятся к протоколу. Громкость в этом раунде не меняли.

В первом живом прогоне «Алиса, панель, сохрани трек» подтверждённый лайк вызвал реплику «Лайк подтверждён» примерно через 4–5 секунд, уже на фоне возобновившейся музыки. После замечания владельца реплика перенесена на приём команды. В повторном живом прогоне владелец принял одно «Сохраняю» сразу, без позднего ответа. В журнале один подтверждённый `music.working` пока операция ещё выполнялась. YouTube подтвердил `like` у точного ID, а Станция продолжила тот же трек на прежней громкости. В обоих прогонах снимали только тестовый лайк и перепроверяли исходное `none`. Тестовые треки поставлены на паузу. Наличие лайка в библиотеке Music отдельно не подтверждено.

## Совместимость с YouTube Music

Desktop OAuth продолжил работать через Happ. В живом повторе браузерного чтения каталог отвечал `503 source_unavailable`. При перепроверке `get_account_info` в ytmusicapi 1.12.4 не нашёл ожидаемое поле и завершился `KeyError`. Ответ browse также не разобрался как прежняя сетка каталога. Эти наблюдения не устанавливают, истекла ли сессия или изменился формат ответа. Настройка прокси и авторизация не менялись.

## Preview и проверки

Изолированный preview по адресу `http://127.0.0.1:8797/music` обслуживает ревизию кода `37a5a587b3ba4d380596f199c975ac6b3c62dc4e` до 26 ноября 10:49:55 МСК. Сборка основана на ветке `codex/music-library-climate-queue`. Временный launcher с диагностическим триггером заменён штатным изолированным launcher. Тестовый защищённый файл удалён, журнал удержания Станции сохранён. Основной порт 8787 обслуживает `2b361918f11ba2ae40805fa65bcdbe1b3f6f99d8`.

Локально прошли `npm run check` (524 unit и 1328 Python-тестов), production build и 11 целевых Playwright-сценариев Music/Climate без пропусков. [Проверки PR #374](https://github.com/decorum-guy/artem-control-center/pull/374/checks). Браузерный шаг Music/Climate выполняется под Linux, Windows проверяет свой runtime. В CI нет шагов выгрузки артефактов.

Для штатной установки нужна отдельная приёмка кандидата. Перенос музыкальной озвучки требует привязки `PANEL_STATION_PLAYBACK_VOICE_ENTITY` к уже настроенной Мини 2. Перед штатным включением голосовой маршрутизации надо остановить изолированный обработчик, чтобы команды обрабатывались в одном процессе.
