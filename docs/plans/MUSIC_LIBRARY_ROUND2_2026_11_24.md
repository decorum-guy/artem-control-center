## 1. Почему Actions не запускались

В предыдущем промпте оркестратор прямо написал «GitHub Actions не запускай». Эта формулировка была перенесена из предыдущих раундов на фоне ограничения тяжёлых артефактов. Отказ от выгрузки видео/дампов сам по себе не требует отключать проверки кода.

В текущем GitHub есть два независимых технических условия пропуска:

1. Head-коммит содержит `[skip ci]`: `Run climate browser checks with the accepted panel profile [skip ci]`. GitHub учитывает такую пометку для обычных push/pull_request запусков. [Коммит](https://github.com/decorum-guy/artem-control-center/commit/8df311aa7bf0bfe10a0a46a880c807a1db5bfedd), [GitHub Docs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/skip-workflow-runs).
2. `.github/workflows/ci.yml` и три остальных workflow фильтруют pull_request по целевой ветке `main`. PR #374 нацелен в `codex/current-track-youtube-music`, поэтому удаление skip-пометки само по себе не включает автоматический CI. [Workflow](https://github.com/decorum-guy/artem-control-center/blob/8df311aa7bf0bfe10a0a46a880c807a1db5bfedd/.github/workflows/ci.yml), [семантика base branch](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#running-your-pull_request-workflow-based-on-the-head-or-base-branch-of-a-pull-request).

Отдельно в `ci.yml` остаются **26 шагов `actions/upload-artifact@v4`**. Это число настроенных шагов, а не измеренный объём хранения и не доказательство 26 успешных загрузок в каждом запуске. Обычный перезапуск прежнего workflow сохраняет риск повторного накопления материалов.

Новые `music-page.spec.ts` и `climate-async.spec.ts` в перечислениях CI пока отсутствуют. `test:e2e:production` по умолчанию запускает только `production-profile.spec.ts`, поэтому не подхватывает их автоматически. В `climate-async.spec.ts` есть skip при отсутствии V2 shell / Overview flags. [Production test runner](https://github.com/decorum-guy/artem-control-center/blob/8df311aa7bf0bfe10a0a46a880c807a1db5bfedd/scripts/test-production-profile.mjs), [climate E2E](https://github.com/decorum-guy/artem-control-center/blob/8df311aa7bf0bfe10a0a46a880c807a1db5bfedd/tests/e2e/climate-async.spec.ts).

Рекомендация нового раунда: вернуть CI после удаления выгрузки тяжёлых файлов; отдельно подключить новые сценарии и обеспечить запуск для цепочки PR. В этом аудите Actions не запускались и workflows не изменялись.

## 2. Что уже получено

По коду и отчёту выполнена основная форма продукта: самостоятельная `/music`, собственный компактный плеер, два блока, каталог YouTube с обложками, отдельные continuation каталога/треков, ограниченная отрисовка и локальный поиск по загруженной части. Старый StationMiniWidget не используется как UI новой страницы.

Исполнитель сообщает о живом чтении 25+15 плейлистов, двух порций по 100 треков, запуске выбранных Яндекс-ID из обоих источников и одной Glagol-сессии при двух вкладках. Для YouTube воспроизводится соответствующая запись Яндекса. Эти результаты не означают прямой YouTube streaming на Mini 2.

В климатическом backend старый пробел прав закрыт: повторная проверка есть после device-lock и ещё перед сервисным POST после fresh-read. Изолированные пробы отзыва прав дали запрет и отсутствие POST. Новая очередь сохраняет температурный draft по ревизии и учитывает выключение. Эти исправления нужно сохранить.

## 3. Подтверждённые недостатки

### R1. Видимые треки теряют действующие ключи запуска — P2

`Feed.rows` ограничен 4500 ключами на провайдера. Кэш до 112 страниц независим от этих ключей; кэшированный ответ возвращается до проверки их сохранности. UI способен сохранять четыре списка по 2400 строк.

Синтетическое воспроизведение на фактическом `music_library.py`:

1. Загрузить A с 2400 записями; первая строка запускается через fake Station.
2. Загрузить B с 2200 записями.
3. Вернуться к сохранённой первой строке A: `409 row_expired`.
4. Повторно GET первой страницы A: возвращается тот же кэшированный объект с тем же невалидным ключом.

В проверке были 47 страниц и 4500 серверных ключей. Числа и треки синтетические; коллекция владельца не копировалась.

Исправить связь срока жизни страниц, отображаемых строк и разрешённых ключей. Одного увеличения константы недостаточно. Видимая доступная строка должна либо иметь действующий ключ, либо безопасно получать новое разрешение своей конкретной позиции без сброса пользовательского списка. Кэшированный ответ не должен бессрочно возвращать неработоспособные ключи. Не ослаблять проверку аккаунта, плейлиста и прав, не вводить произвольные команды от браузера.

Источник: [music_library.py](https://github.com/decorum-guy/artem-control-center/blob/8df311aa7bf0bfe10a0a46a880c807a1db5bfedd/apps/panel-agent/src/panel_agent/music_library.py), `page`/`_project`/`play`.

### R2. Каталог плейлистов нельзя штатно обновить — P2

У кэша страниц нет TTL, а `/catalog` не принимает refresh. После первого чтения изменённый внешний каталог возвращается из старого кэша. Кнопка обновления при выбранном плейлисте обновляет только его треки.

Две синтетические пробы:

- backend: после переименования плейлиста fake provider повторный вызов фактического catalog endpoint оставил старое название; вызов provider.catalog остался один;
- frontend: после добавления NEW в fake response `sync` и действующий refresh handler запросили только status и `tracks/LM?refresh=true`; каталог остался прежним.

Добавить явное обновление каталога и понятное действие в UI. Обновлять связанные продолжения и список известных источников согласованно. При переименовании сохранять выбранный плейлист по ID; при удалении объяснять результат. На временной ошибке сохранять известный каталог с отметкой свежести. Поздние страницы старой ревизии каталога не подмешивать в обновлённую.

Источники: [backend router](https://github.com/decorum-guy/artem-control-center/blob/8df311aa7bf0bfe10a0a46a880c807a1db5bfedd/apps/panel-agent/src/panel_agent/music_library.py#L346-L357), [store](https://github.com/decorum-guy/artem-control-center/blob/8df311aa7bf0bfe10a0a46a880c807a1db5bfedd/apps/dashboard/src/features/music/musicLibraryStore.ts).

### R3. Пятый плейлист сбрасывает поиск и прокрутку — P2

`writeList` удаляет весь TrackList, включая query/scroll. Жертва выбирается по порядку ключей; повторный заход в плейлист не делает его недавно использованным.

Синтетическая проверка точного TypeScript store в Node: задать в A query `Artist` и scroll `640`; пройти A → B → C → D → A → E → A. В конце query пуст и scroll равен нулю. В каждом плейлисте было по 100 тестовых строк. Root повторил этот harness с тем же результатом.

Отделить лёгкое состояние просмотра от тяжёлого кэша треков. Ограничить объём обоих явно и корректно восстанавливать выбранную часть списка. Одного сохранения числа scroll недостаточно, если соответствующая страница уже удалена. Не сбрасывать пользовательское состояние вместе с обычным вытеснением данных.

Окно 2400 строк само по себе не является вечным запретом на ранние треки: в отдельной пробе 2500 строк дали окно 101–2500, а refresh вернул 1–100. Не описывать эту часть как невозможность открыть начало вообще.

Источник: [musicLibraryStore.ts, writeList/select](https://github.com/decorum-guy/artem-control-center/blob/8df311aa7bf0bfe10a0a46a880c807a1db5bfedd/apps/dashboard/src/features/music/musicLibraryStore.ts#L181-L198).

### R4. Зависший availability блокирует отменённую очередь кондиционера — P2

Climate dispatch сначала ждёт `refresh()`; отмену проверяет после его завершения. `fetchHomeAssistantActionAvailability()` не имеет AbortSignal и тайм-аута. Отмена серии очищает хвост, но оставляет running-серию до завершения dispatch, а новые submit в отменённую серию отклоняются.

Синтетическая проба реальных функций hook/dispatch/API с управляемым HTTP: удержать GET availability, отменить очередь блокировкой или read-only, вернуть управление. Новый submit до завершения старого GET — false; после завершения — true; HA POST не было. Это ещё предварительное чтение, не ожидание результата уже отправленной команды. Проба не является полным React/E2E-прогоном.

Передавать отмену серии в предварительный GET и ограничить его время. Завершать отменённое чтение и корректно освобождать серию. Поздний ответ старого чтения не должен менять состояние новой серии. При этом отмена ожидания уже отправленного POST по-прежнему не означает отмену физического действия.

Источники: [ClimateControl dispatch](https://github.com/decorum-guy/artem-control-center/blob/8df311aa7bf0bfe10a0a46a880c807a1db5bfedd/apps/dashboard/src/ClimateControl.tsx#L203-L219), [API client](https://github.com/decorum-guy/artem-control-center/blob/8df311aa7bf0bfe10a0a46a880c807a1db5bfedd/apps/dashboard/src/homeAssistantControlApi.ts#L160-L164), [queue cancellation](https://github.com/decorum-guy/artem-control-center/blob/8df311aa7bf0bfe10a0a46a880c807a1db5bfedd/apps/dashboard/src/useCommandSeries.ts#L47-L54).

### R5. YouTube-подсветка текущей записи теряется при навигации — P3

Подтверждённая пара YouTube → Яндекс хранится только в локальном `matched` компонента MusicPage. Смена плейлиста её сбрасывает, уход со страницы уничтожает компонент. Та же песня может продолжать играть, а строка после возврата больше не подсвечивается. Это вывод из кода; отдельный React-прогон этого случая в аудите не выполнялся.

Хранить подтверждённые соответствия на подходящем уровне с привязкой к аккаунтам и сверять их с актуальным ID Станции. После смены песни старая подсветка не сохраняется. Не подсвечивать совпадение только по названию.

Источник: [MusicPage.tsx](https://github.com/decorum-guy/artem-control-center/blob/8df311aa7bf0bfe10a0a46a880c807a1db5bfedd/apps/dashboard/src/features/music/MusicPage.tsx).

## 4. Следующий раунд реализации

Продолжить актуальный PR #374, сверив новые коммиты. Использовать отдельный worktree при необходимости; не создавать лишнюю цепочку зависимых PR только ради исправлений этого кандидата. Коммиты разделить по музыкальным кэшам/каталогу, состоянию UI, климату и CI.

1. Исправить R1–R4 и добавить адресные регрессии. Устранить R5 вместе с состоянием музыкальной страницы. Сохранить отдельную страницу, новый компактный плеер и текущую семантику голосового сохранения уже играющей песни.
2. Сделать нормальное обновление каталога и восстановление больших списков частью обычного UI. Не требовать перезапуска preview или очистки всех данных для повседневного обновления плейлистов.
3. Подготовить CI без выгрузки тяжёлых артефактов: удалить/отключить upload-artifact шаги, не подменяя их коммитом файлов или новой выгрузкой в другое место. Проверки и их текстовые результаты сохраняются. Действующие тесты и имена обязательных checks не ослаблять ради зелёного статуса.
4. Обеспечить CI текущей цепочки PR. Можно поддержать нужные base branches обычным pull_request либо использовать существующий workflow_dispatch на конкретной ветке после изменения workflow. Не делать merge/retarget в main только ради запуска. Не использовать pull_request_target для исполнения кода кандидата. Перед запуском убедиться, что исполняемая версия уже не выгружает артефакты.
5. Явно добавить в browser gate `tests/e2e/music-page.spec.ts` и `tests/e2e/climate-async.spec.ts` с `VITE_V2_VISUAL_SHELL=true`, `VITE_OVERVIEW_V2_ENABLED=true`, `VITE_V3_VISUAL_SKIN=true`. Проверить, что они исполнились, а не skipped. Указать фактические проверенные SHA, run URL и заключения. CI с fixtures не подключается к домашним устройствам и реальным аккаунтам.
6. Провести ограниченные живые проверки ниже и обновить изолированный preview. Основной runtime остаётся отдельным до решения владельца о штатной установке.

Предлагаемое следующее продуктовое расширение после этих исправлений — аналогичный выбор собственных/понравившихся плейлистов Яндекса с обложками. Первичные API уже разобраны в [исходном плане](LIKED_MUSIC_LIBRARY_2026_11_24.md#2-каталоги-плейлистов-и-чтение-выбранного-списка). Это предложение, а не выявленный дефект #374. Не смешивать его готовность с обязательным исправлением кэшей и CI.

## 5. Приёмка

### Локально и в CI

- R1: A=2400, B=2200; возврат к A и запуск сохранённой строки, повторный GET и восстановление ключа без потери выбора. Проверять больше одного цикла вытеснения, чтобы исключить замену одного малого лимита другим.
- R2: добавление/переименование/удаление плейлиста снаружи, явный refresh каталога, старое продолжение после обновления, ошибка и восстановление.
- R3: A → B → C → D → A → E → A; сохранение поиска и логической позиции с дозагрузкой нужных данных.
- R4: зависший availability → отмена → восстановление → новая команда принимается; старый ответ не повреждает новую серию. Отдельно сохранить проверку неопределённого POST без автоматического replay.
- R5: запустить YouTube-строку → сменить плейлист/раздел → вернуться; подсветка соответствует свежему ID Станции.
- Обе ориентации, отсутствие скачков, ограниченный DOM, проверка прав после lock и перед POST.

### На Samsung и Мини 2

Сначала сверить процесс, ревизию и защищённые настройки. Не менять авторизации, аккаунты или маршруты, если они работают; новые запросы Google/Music продолжают использовать Happ.

Отчёт #374 подтвердил климатический no-op: off при уже off. Нужен один ограниченный прогон, действительно изменяющий разрешённый параметр и подтверждающий новое состояние HA. Не выполнять быстрые циклы включения/выключения. Зафиксировать исходное состояние и восстановить его, если оно не было затем изменено владельцем или другим управлением. Не выдавать HA setpoint за измерение температуры комнаты.

У Станции подтвердить слышимость выбранной песни и один короткий музыкальный голосовой ответ; проверить, что ответ соответствует результату и не оставляет музыку остановленной/переключённой. Протокольный playing и OAuth-valid не заменяют наблюдение звука. Владельца просить только о конкретном необходимом наблюдении; самостоятельную диагностику выполнить самому.

Новые плейлисты/лайки для проверок не создавать без необходимости. Для обновления каталога сначала использовать синтетические сценарии; живое изменение собственной тестовой записи, если оно понадобится, согласовать с текущей приёмкой и убрать только созданное для теста.

## 6. Сдача и ограничения

В отчёте перечислить исправления R1–R5, ссылки на адресные тесты и фактические результаты CI. Отдельно указать живые изменения, наблюдения владельца, что осталось проверить, branch/head/preview и срок жизни процесса. Не переписывать результаты предыдущего исполнителя как собственные наблюдения.

Push напоминаний на iPhone остаётся отдельным открытым пунктом. Уже принятую озвучку напоминания повторять без причины не требуется. Перенос HA на Samsung, изменение VPS/сетевой схемы, merge и штатная установка сюда не входят. Общение — в текущем чате, без новых уведомлений и каналов.

Этот документационный раунд не менял workflows или приложение и не запускал Actions. Он подготавливает конкретную работу следующему исполнителю.
