# Автоматическая установка после main и CI

Запрос владельца от 27.11.2026: [#382](https://github.com/decorum-guy/artem-control-center/issues/382).
Этот документ описывает подготовленный код и первоначальное подключение.
Фактическая установка worker на Samsung и VPS требует доступа к этим хостам;
наличие данного файла не означает, что автоматическая установка уже включена.

## Владельцы кода и цели установки

| Источник | Цель | Что проверяется и устанавливается |
| --- | --- | --- |
| `decorum-guy/artem-control-center`, `main` | Samsung / `control-panel-pc` | Панель через существующий Windows production updater, с точной ревизией и проверкой обслуживаемой сборки. |
| Тот же репозиторий, управляемые HA-файлы | Home Assistant / `ha-vps` | Только явно перечисленные package/component files; образ HA меняется при явно закреплённом digest в manifest. |
| `decorum-guy/AliceTG_Bot`, `main` | `telegram-bot` / `ha-vps` | Собранный образ ровно этого SHA, приватный Compose overlay, health и откат. |

README проекта и исходники AliceTG_Bot подтверждают отдельное владение ботом.
Репозиторий всего HA-стека в доступном discovery не установлен. Действующие
`configuration.yaml`, Compose, secrets и runtime data остаются на сервере.
Первичная настройка связывает проверенные серверные пути с ограниченным набором
исходников в таблице; примеры с `REPLACE` не являются установленными путями.

`kz-bot` остаётся существующим исходящим прокси. Этот выпуск не настраивает его,
не меняет Happ и не требует постоянно включённого Mac.

## Когда разрешена установка

Webhook лишь будит worker. Worker независимо читает GitHub API и проверяет:

1. Имя и числовой ID разрешённого репозитория; активная ветка `main`.
2. Точный текущий SHA этой ветки.
3. Последний push-run каждого обязательного workflow на этом SHA.
4. Успешное завершение всех обязательных именованных jobs и актуальной попытки.
5. Повторную сверку ветки перед передачей SHA локальному исполнителю.

PR, другая ветка, старый зелёный run, `skipped`, незавершённая повторная попытка
или ошибка API не дают разрешения на установку. Workflow запускаются на каждом
push в main без path filters. Имена jobs сверяются автоматическим тестом с
конфигурационными примерами worker.

Обязательный набор панели — шесть jobs четырёх workflows:

| Workflow | Jobs |
| --- | --- |
| `ci.yml` | `Validate (ubuntu-latest)`, `Validate (windows-latest)` |
| `panel-runtime-update.yml` | `Explicit production validation`, `Runtime update browser gate` |
| `kiosk-presence-hotfix.yml` | `Windows dashboard presence regression` |
| `kiosk-process-tree-hotfix.yml` | `Windows Edge process-tree regression` |

У бота требуется `ci.yml` / `validate`. Запуск его CI на main добавлен отдельно
в [AliceTG_Bot PR #45](https://github.com/decorum-guy/AliceTG_Bot/pull/45).
До его включения автоматическая установка бота будет ждать нужные проверки.

## Доставка и отсутствие входящего порта Samsung

VPS получает GitHub `push` и `workflow_run` на единственный HTTPS webhook route.
Внутренний обработчик слушает loopback и проверяет HMAC SHA-256, разрешённый
репозиторий, тип события, ветку, размер запроса и уникальный delivery ID.
Внешний запрос не выбирает команду, программу, URL, сервис или файловый путь.

Samsung раз в минуту сам сверяется с GitHub. Это также восстанавливает работу
после пропущенного события или временного отключения ноутбука. VPS выполняет
такую же периодическую сверку дополнительно к webhook. Установка начинается
после успешной сверки; минута — интервал проверки, не обещание времени сборки.

GitHub описывает [подпись webhook](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries),
[повторные delivery ID и короткий ответ обработчика](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks),
а также [фильтрацию workflow runs по ветке, событию и SHA](https://docs.github.com/en/rest/actions/workflow-runs).

## Что происходит при установке и отказе

Состояние попыток хранится локально вне Git. На узле работает один установщик;
повторный webhook и параллельный запуск не создают вторую установку. Новый push
не прерывает уже начатую операцию. Следующая сверка рассматривает актуальный main.

Windows-адаптер передаёт проверенные `ExpectedCurrentHead`, `ExpectedTargetHead`
и `RequestId` существующему updater. Тот сохраняет staging, maintenance lease,
проверки сборки и откат. Сам факт запуска дочернего PowerShell или завершение
первого процесса не считаются результатом: updater может передавать работу
процессу из новой ревизии. Нужны его итог по данному request и фактические
readiness / served build identity.

Серверный адаптер действует адресно. Для бота проверяются текущая готовность,
резервная копия Planning, image identity, приватные listeners и новая готовность.
Для HA подготавливаются только управляемые файлы, проверяется конфигурация в
изолированном контейнере и сохраняется материал для отката. Изменение образа
использует digest и отдельную согласованную политику резервирования состояния.

Неопределённый результат после начала записи блокирует дальнейшие установки до
проверки оператора. Команда с возможным выполнением не повторяется автоматически.
Нормальный откат и его health отличаются от неопределённого исхода. Подробные
коды, статус и восстановление описаны рядом с исполняемыми файлами.

## Одноразовое подключение локальным агентом

Использовать существующие `ssh control-panel-pc` и `ssh ha-vps`, сверить реальные
пути, пользователя и версии. Инструкции с командами и конфигурационными примерами:

- [Worker, webhook и Samsung task](../scripts/auto-deploy/README.md).
- [Адресные серверные исполнители, backup и rollback](../integration-patches/auto-deploy/README.md).
- [Штатный Windows updater](WINDOWS_PRODUCTION_RUNTIME.md).
- [Голосовая яркость и её HA-компонент](ALICE_PANEL_BRIGHTNESS.md).

Worker и адаптеры устанавливаются в постоянный каталог вне меняющегося checkout.
Секреты хранятся отдельными защищёнными файлами; для GitHub достаточно чтения
Contents/Actions/Metadata нужных репозиториев. В браузер, логи и webhook URL
токены не попадают. Примеры поставляются с отключёнными targets.

После первоначальной установки, проверки путей/секретов и включения конкретных
targets новые зелёные main устанавливаются без команды локального агента.
Ручное управление runtime и намеренная остановка панели сохраняются. Для
отключения останавливается worker/task; выполняющаяся транзакция сначала должна
завершиться или быть восстановлена по своему журналу.

## Приёмка на реальных хостах

- Зафиксировать установленные SHA и резервные копии до включения.
- Проверить `status`, закрытые targets и отклонение неверной подписи webhook.
- На согласованном выпуске подтвердить прохождение exact-SHA CI и установку
  Samsung без Mac; сверить фактический `/api/v1/system/production-build` и readiness.
- Проверить отдельное обновление бота и управляемого HA package, остальные
  Compose services и приватные forwards.
- Проверить дубликат события, временный offline, новый push во время сборки,
  известный откат и блокировку неопределённой операции в изолированном контуре.
- Не создавать неисправный production выпуск специально для проверки отката.

Автоматические тесты используют контролируемые GitHub/процессные/HA ответы.
Они не доказывают настройку Caddy, Windows Task Scheduler, Docker или распознавание
голоса в доме. Реальные результаты нужно дописать после локальной установки.
